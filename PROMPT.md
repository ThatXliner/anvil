# Claude Code Prompt: Anvil — GitHub-Compatible API for Your Forgejo Instance

## What Anvil Is

Anvil is a **product**, not a framework. It lets you point GitHub-expecting tools at your Forgejo instance. Two minutes from install to a working `gh` CLI against Forgejo.

Under the hood, Anvil is just **Shotgun configured for GitHub↔Forgejo**. Shotgun is the project that lives in ../shotgun. The value is the curated mapping file, the one-command experience, and the testing. How it's packaged — shell script, Docker image, Makefile, Nix flake, Rust wrapper, whatever — is an implementation detail. Claude Code should pick whatever makes the "two minutes to working" promise easiest to deliver.

## What Anvil Ships

1. **A tested `mappings.toml`** — initially generated by `shotgun init` against the GitHub and Forgejo OpenAPI specs, then hand-reviewed and corrected for every important endpoint. This is the core deliverable.
2. **The bundled specs** — `github-rest-api.json` and `forgejo-api.json`, pinned to known-good versions.
3. **A one-command entrypoint** — the user provides their Forgejo URL and runs one command. Everything else is handled.
4. **Documentation** — what works, what doesn't, and what to do about it.

## The User Experience

```bash
# However Anvil is packaged, the experience is:
anvil --forgejo-url https://git.example.com

# Or maybe it's:
docker run -e FORGEJO_URL=https://git.example.com ghcr.io/yourorg/anvil

# Or maybe it's:
FORGEJO_URL=https://git.example.com ./anvil.sh

# Then:
GH_HOST=localhost:3000 gh repo list
GH_HOST=localhost:3000 gh issue create --title "Test" --body "It works"
```

That's the entire product. The user doesn't need to know about Shotgun, OpenAPI specs, or mapping files.

## IMPORTANT: Research the Actual APIs

**Before writing the mapping file, you MUST research the actual API differences yourself.** Do not guess.

1. **Fetch GitHub's REST API spec.** The OpenAPI description is at `github/rest-api-description` on GitHub.
2. **Fetch Forgejo's API spec.** Any Forgejo instance serves it at `/api/v1/swagger.json`. Use Codeberg's public instance: `https://codeberg.org/api/v1/swagger.json`.
3. **For each Priority 1 endpoint**, compare the request and response schemas between the two specs. Document every difference: field renames, missing fields, type differences, structural mismatches.
4. **Look at what the `gh` CLI actually reads.** Search the `cli/cli` GitHub repo to see which response fields the `gh` tool depends on. These are the fields that must be correct.
5. **Test against real responses if possible.** Codeberg is a public Forgejo instance — you can hit its API (with rate limiting) to see what real responses look like.

Build the mapping file from what you find, not from assumptions.

### Things to Investigate Specifically

- User object: field name differences (`name` vs `full_name`, `created_at` vs `created`, presence of `node_id`)
- Repository object: GitHub's `homepage` vs Forgejo's `website`, nested owner object shape
- PR merge endpoint: GitHub uses `PUT`, Forgejo uses `POST` — can Shotgun's mapping format express method differences? If not, this needs to be added to Shotgun first.
- Pagination: `per_page` vs `limit`, Link header URL rewriting
- Rate limit headers: GitHub returns `X-RateLimit-*`, Forgejo doesn't — can Shotgun synthesize headers? If not, this may need to be a Shotgun feature.
- Auth: both accept `Authorization: token X` but there may be edge cases

**If you find that Shotgun's mapping format can't express something the GitHub↔Forgejo translation needs, go add the feature to Shotgun first.** Anvil is the use case that drives Shotgun's feature development. Don't work around Shotgun's limitations in Anvil — fix them upstream.

## Priority 1 Endpoints

These must work correctly. They're what `gh` CLI, Renovate, basic CI tools, and deploy hooks actually hit.

**User / Auth:**
- `GET /user`
- `GET /users/{username}`

**Repositories:**
- `GET /repos/{owner}/{repo}`
- `GET /user/repos`
- `GET /users/{username}/repos`
- `GET /orgs/{org}/repos`
- `POST /user/repos`
- `GET /repos/{owner}/{repo}/branches`

**Issues:**
- `GET /repos/{owner}/{repo}/issues`
- `POST /repos/{owner}/{repo}/issues`
- `GET /repos/{owner}/{repo}/issues/{number}`
- `PATCH /repos/{owner}/{repo}/issues/{number}`
- `GET /repos/{owner}/{repo}/issues/{number}/comments`
- `POST /repos/{owner}/{repo}/issues/{number}/comments`

**Pull Requests:**
- `GET /repos/{owner}/{repo}/pulls`
- `POST /repos/{owner}/{repo}/pulls`
- `GET /repos/{owner}/{repo}/pulls/{number}`
- `PATCH /repos/{owner}/{repo}/pulls/{number}`
- `PUT /repos/{owner}/{repo}/pulls/{number}/merge`

**Commit Status (CI surface):**
- `POST /repos/{owner}/{repo}/statuses/{sha}`
- `GET /repos/{owner}/{repo}/commits/{ref}/status`

**Contents:**
- `GET /repos/{owner}/{repo}/contents/{path}`
- `GET /repos/{owner}/{repo}/readme`

## Priority 2 (after P1 works end-to-end)

Labels, milestones, releases, webhooks management, org membership, git refs/tags, collaborators, search endpoints.

## Explicitly Not Supported

These should return a clear 501 with a helpful message:

- GitHub Apps / installation tokens
- GraphQL API (`/graphql`)
- GitHub Packages
- Code scanning / security advisories

That being said, we should still support

- GitHub Actions API
- Dependabot API
- Codespaces API

## Validation

The mapping file isn't done until these work:

```bash
# All of these through the proxy:
gh auth status
gh repo list
gh repo view {owner}/{repo}
gh issue list -R {owner}/{repo}
gh issue create -R {owner}/{repo} --title "Test" --body "Body"
gh pr list -R {owner}/{repo}
gh pr view {number} -R {owner}/{repo}
```

Write a test script that runs these against a real Forgejo instance (or a mock) through Anvil and checks the output.
